4. ¿Hicimos un buen trabajo?

  1. ¿Cuántos requisitos cumplen de los 25? 0 de 25. Juice Shop es vulnerable por diseño; el valor del ejercicio está en la evidencia, no en el resultado. Solo se salvan controles puntuales, como el enmascarado de tarjetas en payment.ts:32 o el saneamiento de comentarios en feedback.ts:44, pero no alcanzan para declarar una fila completa.
  2. ¿Qué encontró la revisión humana que ninguna herramienta encontró? El BOLA del carrito (basket.ts:19), el saldo incrementable desde el cliente (wallet.ts:27), el MD5 para contraseñas (insecurity.ts:41) y la autorización por función ausente: con un token customer, GET /rest/user/authentication-details devuelve 200 con los correos de todos los usuarios. Semgrep no tiene una regla que sepa a quién pertenece un objeto, y ZAP sin sesión nunca llega a esas rutas. También fue humana la lectura de que Access-Control-Allow-Origin: * era inofensivo en este contexto: ZAP lo marcó Medium.
  3. ¿Qué falso positivo les hizo perder más tiempo? El de Cross-Domain Misconfiguration de ZAP. La alerta sugiere fuga de datos entre dominios, pero sin Access-Control-Allow-Credentials: true el navegador no envía cookies y los recursos marcados son públicos (polyfills.js, robots.txt, sitemap.xml). Tocar ese header no habría cambiado el riesgo real; el esfuerzo se fue en confirmar que no había una segunda cabecera.

Lo que Semgrep no encontró

Esto es tan importante como lo que sí encontró:

  • BOLA en el carrito (basket.ts:19): no hay regla que sepa que id debe pertenecer al usuario.
  • Campos sensibles escribibles (wallet.ts:27): el incremento de saldo con un monto del cliente no coincide con ningún patrón conocido.
  • MD5 para contraseñas (insecurity.ts:41): p/owasp-top-ten no lo marcó.
  • La llave privada literal (insecurity.ts:21): p/secrets reportó su uso en la línea 54, no el secreto en sí.
  • Cookie sin Secure/HttpOnly/SameSite (insecurity.ts:192).
  • Ausencia de HSTS y de cabeceras de seguridad: eso lo cubre el DAST, no el SAST.

Estos seis puntos salieron de la revisión humana de la sección 1.

1. Método: de la alerta al criterio

Una herramienta no emite criterio, emite señales. El criterio se construye en cinco pasos y ninguno se puede saltar:

Paso Pregunta Evidencia que lo respalda Ejemplo en este laboratorio
1. Detectar ¿Qué dijo la herramienta? Reporte crudo (semgrep.sarif, zap.json) Semgrep marca search.ts:23 como warning
2. Reproducir ¿Puedo provocarlo yo? Comando y salida GET /rest/products/search?q=' OR '1'='1 devuelve todo el catálogo
3. Clasificar ¿Es real? Verdadero o falso positivo, con la razón 8 de 8 en Semgrep; 1 falso positivo en ZAP
4. Valorar ¿Cuánto importa aquí? Impacto × probabilidad, justificados La SQLi es crítica; el CORS es riesgo 1
5. Decidir ¿Corregir, mitigar, aceptar o transferir? Requisito ASVS + control + prueba BOLA: corregido y demostrado

Regla de trabajo: si un hallazgo no se reproduce en el paso 2, no se afirma en el paso 3. «Lo dice la herramienta» no es evidencia; la evidencia es la petición, el archivo y la salida.

Por qué no se usa la severidad de la herramienta como criterio

Tres casos de este mismo escaneo lo demuestran:

Caso Lo que dijo la herramienta Lo que dice el criterio
SQLi en search.ts:23 Semgrep: warning (ni siquiera error) Riesgo 25/25: lectura y escritura de toda la base, sin autenticación
Access-Control-Allow-Origin: * ZAP: Medium Riesgo 1/25: falso positivo, no hay Allow-Credentials
BOLA en basket.ts:19 Ninguna herramienta lo vio Riesgo 16/25: cualquier usuario lee el carrito de otro

La severidad de la herramienta describe el patrón, no el contexto. El criterio es lo que convierte el patrón en una decisión.

Impacto (1–5)

Valor Significado Ejemplo

4.3 Por qué cada herramienta ve lo que ve

Semgrep razona sobre el código. Ve patrones peligrosos aunque la ruta nunca se ejecute, por eso encuentra los cuatro sendFile que la revisión humana pasó por alto. No puede ver: - Propiedad de los datos (BOLA): no hay patrón que diga que id debe pertenecer al usuario. - Lógica de negocio: que un saldo no puede venir del cliente no es una regla sintáctica. - Estado de configuración: HSTS, CSP y CORS viven en el servidor, no en el repositorio. - El secreto literal: p/secrets reporta el uso de la llave en la línea 54, no la llave en la 21.

ZAP razona sobre respuestas HTTP. Es el único que ve las cabeceras que faltan y el que mide 61 pruebas pasivas. No puede ver: - Nada detrás del login: sin sesión, /rest/basket/{id} responde 401 y el BOLA queda invisible. - El modelo de datos: no sabe que el carrito 9 pertenece a otro usuario. - Inyección: el escaneo baseline es pasivo; no fuzzea q ni construye cargas. - Lógica de negocio: no intenta una cantidad negativa ni un rol admin.

La revisión humana razona sobre el diseño. Es la única que encontró BOLA, saldo, rol, MD5, cookies, rate limit y logging. Su debilidad es la opuesta: no es exhaustiva. Se le escaparon cuatro rutas con sendFile que Semgrep sí encontró, y no puede repetirse igual dos veces.

5.3 El patrón de un cierre demostrable

Sirve para cualquiera de los hallazgos anteriores:

  1. Reproducir la falla con un comando o una prueba que falle (rojo).
  2. Aplicar el control en el punto exacto, no después de cargar el dato.
  3. Probar que el ataque falla (verde) y que el uso legítimo sigue funcionando (regresión).
  4. Cubrir el borde: sin sesión, recurso inexistente, identificador no numérico.
  5. Guardar la evidencia: commit, comando, salida y enlace al PR.

Una corrección sin los pasos 1 y 3 es una opinión, no una demostración.

1. Autorización por función · ASVS 8.3.1

La falla

GET /rest/user/authentication-details exige sesión (sin token responde 401), pero no comprueba el rol. Cualquier usuario customer recibe la lista completa de usuarios con correo, rol e IP del último inicio de sesión:

GET /rest/user/authentication-details
Authorization: Bearer <token de customer>
→ HTTP 200
{"status":"success","data":[{"id":1,"email":"admin@juice-sh.op","role":"admin", ...}]}

app-src/routes/authenticatedUsers.ts:10 ejecuta UserModel.findAll() sin mirar quién pregunta. security.isAuthorized existe en app-src/lib/insecurity.ts:52, pero ninguna ruta lo usa para verificar roles.

El control

async function retrieveUserList (req: Request, res: Response, next: NextFunction) {
  try {
    // Control ASVS 5.0 · 8.3.1: solo un administrador puede listar a todos los usuarios.
    const requester = security.authenticatedUsers.from(req)
    if (requester?.data?.role !== 'admin') {
      res.status(403).json({ status: 'error', message: 'Forbidden' })
      return
    }

    const users = await UserModel.findAll()

Decisiones:

  • 403 y no 404: el recurso existe y el usuario está autenticado; ocultar la ruta no aporta y rompería la semántica de la API.
  • El rol se lee de la sesión del servidor, no de un campo del cuerpo ni del cliente.
  • Falla cerrado: si la sesión no está en el mapa, no hay rol y se responde 403.

La falla

POST /api/BasketItems acepta quantity negativa o cero. La validación de app-src/routes/basketItems.ts:94 solo comprueba stock:

Con quantity: -2 la orden se crea y order.ts:93 calcula itemPrice * quantity, produciendo un total negativo. Es la amenaza T01 del Lab 1.

El control

async function quantityCheck (req: Request, res: Response, next: NextFunction, id: number, quantity: number) {
  const quantityNumber = Number(quantity)
  // Control ASVS 5.0 · 2.3.2: la cantidad debe ser un entero positivo y acotado.
  if (!Number.isInteger(quantityNumber) || quantityNumber <= 0 || quantityNumber > 1000) {
    res.status(400).json({ error: 'Invalid quantity' })
    return
  }

  const product = await QuantityModel.findOne({ where: { ProductId: id } })

Decisiones:

  • Validar en quantityCheck cubre creación y actualización: los dos middlewares (quantityCheckBeforeBasketItemAddition y …Update) pasan por la misma función.
  • Entero, no decimal: una fracción de ítem tampoco es una línea de pedido válida.
  • Tope de 1000: el límite real de stock se sigue aplicando después; el tope evita valores absurdos que desborden el cálculo.

2. Descripción de la falla

app-src/routes/basket.ts buscaba el carrito solo por el id de la URL:

const id = req.params.id
const basket = await BasketModel.findOne({ where: { id }, include: [...] })

No comparaba ese id con el usuario autenticado. Cualquier sesión válida podía leer el carrito de otra persona cambiando el número en la URL. El bloque challengeUtils.solveIf(...) detectaba el acceso indebido, pero no lo bloqueaba.

Prueba previa al cambio:

AssertionError: 200 != 404 : BOLA: el usuario A leyó el carrito 9 del usuario B
(UserId 30) con HTTP 200: {"status":"success","data":{"id":9,...,"UserId":30,...}}

3. Cambio aplicado

app-src/routes/basket.ts:

-      const basket = await BasketModel.findOne({ where: { id }, include: [...] })
+      const user = security.authenticatedUsers.from(req)
       challengeUtils.solveIf(challenges.basketAccessChallenge, () => {
-        const user = security.authenticatedUsers.from(req)
         const isValidId = id && id !== 'undefined' && id !== 'null' && id !== 'NaN'
         return user && isValidId && user.bid && user?.bid != parseInt(id, 10)
       })
+
+      // Control ASVS 5.0 · 8.2.2: el carrito debe pertenecer al usuario autenticado.
+      if (user == null) {
+        res.status(401).json({ status: 'error', message: 'Unauthorized' })
+        return
+      }
+      if (!Number.isInteger(Number(id))) {
+        res.status(404).json({ status: 'error', message: 'Basket not found' })
+        return
+      }
+
+      const basket = await BasketModel.findOne({ where: { id, UserId: user.data.id }, include: [...] })
+
+      // Ajeno e inexistente responden igual: no se filtra la existencia del recurso.
+      if (basket == null) {
+        res.status(404).json({ status: 'error', message: 'Basket not found' })
+        return
+      }

Decisiones de diseño:

  • 404 en lugar de 403 para un carrito ajeno: así el atacante no puede distinguir «existe pero no es mío» de «no existe», que es lo que pedía el requisito verificable del Lab 1.
  • Sin token → 401, coherente con el resto de la API.
  • id no numérico → 404, para no llegar nunca a la consulta.
  • El filtro se aplica en la consulta (where: { id, UserId }), no después de traer el registro: el objeto ajeno no se carga en memoria.
